# MVP 里程碑治理标准（跨项目通用 v1）

## 1. 目标
所有复杂项目必须以“可交付的 MVP 闭环”作为里程碑推进单位。  
每个里程碑必须可验收、可复盘、可迭代，不以“功能数量”作为完成标准。

## 2. 里程碑定义
一个里程碑必须同时满足以下条件：
- 有明确业务目标（目标用户 + 目标结果）。
- 有清晰范围边界（做 / 不做）。
- 有可量化门禁（验收指标与失败条件）。
- 有完整链路（触发 -> 处理 -> 结果 -> 验证）。
- 有运行记录（日志、缺陷、决策记录）。

## 3. 里程碑门禁（必须全部通过）
- 功能门禁：关键场景可执行且结果可见。
- 数据门禁：输入、处理、输出一致，关键字段完整。
- 质量门禁：主链路通过回归，关键缺陷为 0。
- 稳定门禁：连续 N 次（建议 3 次）闭环成功。
- 运营门禁：异常可定位、风险可追踪、回滚方案可执行。

## 4. 任务拆解标准（每个里程碑）
- 拆为 5 类任务：架构、UI/UX、前端、后端、测试。
- 每类任务拆为“可交付最小单元”，每个单元 0.5~2 天。
- 每个任务必须有：负责人、输入、输出、完成定义（DoD）、验证方式。
- 禁止把“探索性想法”直接混入里程碑主链路。

## 5. 子代理分配标准（能力匹配）
分配任务前先判断三个维度：
- 领域匹配：角色职责是否直接覆盖任务类型。
- 工具匹配：是否具备对应 skill / MCP 能力。
- 风险匹配：任务风险是否超过该代理当前能力等级。

分配规则：
- 高风险任务：必须由对应专家代理主责，必要时主代理兜底。
- 中风险任务：专家代理执行，PM 代理跟踪门禁。
- 低风险任务：可并行分配，按时限合并结果。

## 6. 子代理能力分级（持续升级）
- L1：可执行标准任务（有模板、有明确输入输出）。
- L2：可独立处理常见变体并给出风险提示。
- L3：可主导子领域方案并进行质量自检。
- L4：可定义子领域标准并指导其他代理协作。

每次里程碑结束后，按以下信号升级或降级：
- 任务一次通过率
- 返工率
- 缺陷密度
- 交付时效
- 风险预判准确率

## 7. 里程碑复盘机制（每次闭环必须做）
复盘输出必须包含：
- 目标达成：达成 / 部分达成 / 未达成
- 偏差分析：范围偏差、质量偏差、节奏偏差
- 根因分类：需求、设计、实现、测试、协作
- 优化动作：下个里程碑要执行的 3 条硬动作
- 能力调整：子代理能力等级变化与原因

## 8. 与项目管理自动化的对齐
自动化任务必须固定输出：
- 当前里程碑目标与门禁状态
- 当日 TODO / DOING / DONE / RISK / BLOCKED
- 子代理任务分配与能力匹配结论
- 里程碑风险变化与升级建议
- 下一步最高优先级动作（仅 1 条）

建议自动化节奏：
- 日报：工作日固定时段同步门禁状态。
- 周报：每周固定一次里程碑健康检查。
- 结项：每个里程碑完成后自动触发复盘模板。

## 9. 当前项目默认执行约束（Forecasting_Algorithm）
- 当前最高优先级里程碑：SPU MVP 闭环。
- 非闭环项（增强图表、复杂告警、深度优化）默认后置。
- 所有分配与验收先服从“闭环稳定通过”。

## 10. 项目/里程碑启动触发模板（强制）
每个项目开始，或每个里程碑开始，必须先由 PM 发起以下模板并等待确认：

```text
目标：这次要达成什么结果（一句话）。
范围：做什么，不做什么。
优先级：P0/P1/P2（只给一个主优先级）。
验收：什么算完成（最好可量化）。
时限：希望什么时候交付（日期或“本周内”）。
约束：必须遵守的限制（比如“不改数据库结构”）。
```

执行规则：
- 未完成模板确认，不进入开发执行。
- 若执行中范围发生变化，必须重新发起模板确认。
- 模板确认记录应写入当期里程碑看板或周报。

## 11. 第一性原则执行条款（强制）
所有项目讨论、方案设计、任务分配、验收复盘，默认遵守以下条款：
- 从原始需求和问题本质出发，不从历史习惯或模板惯性出发。
- 不预设“需求方一定表达完整”；当目标或动机不清晰时，必须先确认再执行。
- 当当前路径不是最优路径时，必须直接给出更优替代方案与取舍理由。
- 遇到问题优先追根因，不以“补丁堆叠”替代根因修复。
- 关键决策必须能回答“为什么”，并记录在里程碑日志或复盘结论中。
- 汇报输出只保留影响决策的信息，避免无关信息干扰判断。
