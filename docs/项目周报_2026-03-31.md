## 问题与障碍

### 当前问题

1. **测试工程师资源**
   - 问题描述: 测试工程师资源需要确认
   - 影响: 测试无法进行
   - 缓解措施: 提前沟通，确认资源

2. **Linux 正式环境仍有数据库权限阻塞**
   - 问题描述: 当前 `ai_reader` 对 `lx_ods` schema 无读权限，手工预测触发后在查数阶段失败
   - 影响: 前端可打开，但正式预测任务暂不能完整跑通
   - 缓解措施: DBA 执行 schema/table 授权后再次手工验收

3. **前端仍存在旧统计口径残留**
   - 问题描述: 历史运行页面中曾出现 `1224/1366` 等旧口径目标数，与当前“108 周以上 SPU”真实口径不一致
   - 影响: 容易误判正式批量规模和总耗时
   - 缓解措施: 统一改为按周去重后的真实 SPU 统计，并同步到 Linux 正式环境

### 待解决问题

1. **告警通知方式**
   - 问题描述: 需要确认告警通知方式（邮件/钉钉/企业微信）
   - 影响: 告警功能不完整
   - 处理计划: 下期实现

2. **交互式图表库选择**
   - 问题描述: 需要确认交互式图表库（Plotly/Bokeh）
   - 影响: 图表功能无法开发
   - 处理计划: 下期确认

3. **Linux 常驻服务与每周作业时间尚未最终落地**
   - 问题描述: 前端/API 仍需切换为 `systemd` 常驻服务；每周自动预测需固定为每周一 01:00，并完成 Linux timer 同步
   - 影响: 页面无法保证长期在线，自动作业时间与前端展示时间可能不一致
   - 处理计划: 明日优先完成 `forecast-dashboard-v2.service`、`forecast-weekly.timer` 的正式配置与验收

4. **当前不调整算法范围**
   - 问题描述: 业务要求以预测准确率为核心，不希望为了时长阉割 `smart` 算法能力
   - 影响: 后续上线评估应基于真实 `35` 个 SPU 的整体时长，而不是单个 SPU 绝对耗时
   - 处理计划: 在 Linux 正式口径下完成一轮真实批量验收后，再决定是否需要进一步优化执行链路
